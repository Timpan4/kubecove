# Frontend feature parity

The Svelte web frontend and the GPUI native client share one set of UI acceptance tests. Each file in `scenarios/` declares scenarios, and both drivers run every scenario against the same data:

- `web.ts` drives the Svelte app in Chromium with the browser mocks from `src/lib/tauri-dev-mocks.ts`.
- `src-tauri/gpui/tests/parity.rs` drives the GPUI client offscreen with `visual/export-fixture.ts`'s export of those same mock responses, through `src-tauri/gpui/tests/common/`.

`bun run e2e:parity` exports the fixture, runs both drivers and passes only when both report every scenario as passed. A passing mock scenario proves UI integration through the command seam, not a real Kubernetes request or a packaged application.

## Focused checks

Run new scenarios in each driver before the full suite. This catches missing native test registration and driver input mistakes without rerunning unrelated views. From the worktree root, with its local TMPDIR already set:

1. Run a web scenario prefix. This example checks the kind picker and records screenshots and `web.json`.

   ```sh
   mkdir -p e2e/artifacts/parity-focus
   PARITY_PREFIX=kind-picker nice -n 10 bun -e 'import { loadContract } from "./e2e/parity/contract"; import { runWeb } from "./e2e/parity/web"; const contract = await loadContract(); await runWeb({ scenarios: contract.scenarios.filter((scenario) => scenario.id.startsWith(process.env.PARITY_PREFIX ?? "")) }, `${process.cwd()}/e2e/artifacts/parity-focus`, new AbortController().signal);'
   ```

2. Export the same fixture and run that prefix offscreen in GPUI. The native input helper sends Backspace for an empty replacement; typing an empty string does not clear an input.

   ```sh
   bun e2e/parity/visual/export-fixture.ts e2e/artifacts/parity-focus/fixture.json
   KUBECOVE_PARITY_FIXTURE="$PWD/e2e/artifacts/parity-focus/fixture.json" \
   KUBECOVE_E2E_ARTIFACTS="$PWD/e2e/artifacts/parity-focus" \
   KUBECOVE_PARITY_SCENARIO_PREFIX=kind-picker \
   CARGO_TARGET_DIR="$PWD/src-tauri/gpui/target" \
   CARGO_BUILD_BUILD_DIR="$PWD/src-tauri/gpui/build" \
   CARGO_BUILD_JOBS=1 nice -n 10 \
   cargo test --manifest-path src-tauri/gpui/Cargo.toml --test parity
   ```

3. Leave the unfiltered suite to CI: `.github/workflows/parity.yml` runs it after each merge to main and runs the changed-file selection (below) on every PR, split across `PARITY_SUITE_SHARD` jobs that each upload their `e2e/artifacts/parity-*` directory. The Verification tiers in `AGENTS.md` describe the local checks. Focused reports prove only the scenarios they name.

`bun run e2e:parity` runs both drivers at the same time. The web driver runs several pages at once, and the GPUI driver builds the parity test once and runs it in several processes (`KUBECOVE_PARITY_SHARD=<index>/<count>`). The web driver starts at once, and the GPUI build runs while the runner exports `fixture.json`; only the GPUI test processes wait for the fixture. The GPUI processes take scenarios from a shared queue: each claims the next unclaimed scenario by creating `gpui-claims/<position in scenarios.txt>`, which holds its shard index. Each writes `gpui-<index>.json` and the runner merges them into `gpui.json`. Both reports record each scenario's `durationMs`, and `result.json` records the seconds from the start of the run to the end of each phase under `phases`. Optional variables:

- `PARITY_PREFIX=overview,launcher-errors.` runs scenarios whose IDs start with any listed prefix.
- `PARITY_CHANGED=<base ref>` runs the scenarios that the changes since the merge base with that ref can affect, including uncommitted and untracked files. See "Change-based selection". `PARITY_COVERAGE_MAP=<path>` reads another map than `e2e/artifacts/parity-coverage-map.json`.
- `PARITY_COVERAGE=1` records the coverage map that `PARITY_CHANGED` reads. See "Change-based selection".
- `PARITY_RERUN=last` (or an artifacts directory) runs only the scenarios that either driver did not pass in that run.
- `PARITY_SUITE_SHARD=<index>/<count>` runs every `count`-th selected scenario from position `index`, so separate CI jobs split one suite. It applies after the other filters.
- `PARITY_JOBS=<n>` sets the pages and processes per driver. The default is half the CPU count, because both drivers share the CPUs.

Scenarios in one GPUI process share that process, so a scenario that passes alone can fail after another scenario leaves state behind. Treat such an order-dependent failure as a test isolation bug. To replay one shard of a run, write the IDs from that run's `gpui-<index>.json` to a file, one per line, and give the parity test binary that file without `KUBECOVE_PARITY_SHARD`: `KUBECOVE_PARITY_SCENARIO_IDS=<file> KUBECOVE_PARITY_FIXTURE=<run>/fixture.json KUBECOVE_E2E_ARTIFACTS=<new directory> <parity test binary> --nocapture`. A shard claims scenarios in `scenarios.txt` order, so the replay runs them in the same order. If the shard stopped before writing its report, the claim files that hold its index name its scenarios. The binary path is in the run's `gpui-build.log`. A file with two IDs checks one ordering.

## Change-based selection

A `PARITY_COVERAGE=1` run records which source lines each scenario executed and writes `coverage-map.json` to its artifacts directory. An unfiltered run also copies the map to `e2e/artifacts/parity-coverage-map.json`, where `PARITY_CHANGED` reads it. Coverage is off in normal runs.

- Web: Chromium block coverage through Playwright, per page, mapped to source lines through the inline source maps Vite serves (`web-coverage-map.ts`).
- GPUI: the parity test is built with `-C instrument-coverage --cfg kubecove_coverage` in `<CARGO_TARGET_DIR>/coverage`, so the normal build stays. Each scenario resets the counters and writes its own profile (`tests/parity/code_coverage.rs`), which `llvm-profdata` and `llvm-cov export` turn into lines (`gpui-coverage-map.ts`). The tools come from `LLVM_PROFDATA` and `LLVM_COV`, else the rustup `llvm-tools` component, else `PATH`. Cargo dep-info lists every repository file the binary compiled.

Only scenarios that both drivers passed enter the map. `PARITY_CHANGED` diffs the merge base against the working tree and selects (`changed-scenarios.ts`):

- the full suite when the map is missing, its commit is not in the clone, or a file changed that coverage cannot see: `package.json`, `bun.lock`, `Cargo.toml` and `Cargo.lock` files, `build.rs`, `vite.config.ts` and the scripts it imports, tsconfig files, `index.html`, `public/`, everything under `e2e/parity/` except scenario files and Markdown, `scripts/e2e-parity.ts` and the process helper it imports, `src-tauri/gpui/tests/parity.rs`, `tests/parity/` and `tests/common/`, the parity workflows, a non-Rust file the GPUI binary compiles in (such as an `include_bytes!` asset), or a non-code file under `src/` that no scenario loaded;
- every scenario in a changed scenario file, and every scenario the map does not hold;
- for other files, the scenarios that executed the changed lines. Changed lines are translated to the map's commit first, so a map from an older main commit still applies.

Lines need care by file kind:

- TypeScript: line level. A module's top-level code runs for every scenario that imports it, so changes there select all of those scenarios.
- Svelte: line level inside `<script>`; a markup or style change selects the scenarios that rendered the component.
- Rust: line level inside coverage regions. Changes outside them, such as constants, types and imports, select the scenarios that executed any code in that file or in a file naming a changed item.
- Comment-only and blank-line changes in Rust and TypeScript select nothing.

Mock data (`src/lib/tauri-dev-mock*.ts`, `src/lib/mcp-dev-mocks.ts`) is selected through the web driver's coverage of the same scenario. The GPUI driver reads the mocks only through the exported fixture, which runs every mock at once, so a scenario whose GPUI run reads a mock response that its web run never requests is not selected for that change. Both drivers run the same steps against the same data, so this has not been seen; the fixture exporter itself is a full-suite file.

CI: the main job runs the full suite with `PARITY_COVERAGE=1`, and the `coverage-map` job merges the shard maps (`bun e2e/parity/coverage-map.ts merge <out> <shard maps>`) and saves the result with `actions/cache` under `parity-coverage-map-<sha>`. Pull request jobs restore the map of their base commit, or else the newest one, because caches saved on the default branch are readable from pull requests ([GitHub docs](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching#restrictions-for-accessing-a-cache)). The merged map is also uploaded as the `parity-coverage-map` artifact. To use it locally:

```sh
run=$(gh run list --repo Timpan4/kubecove --workflow parity.yml --branch main --event push --status success --limit 1 --json databaseId --jq '.[0].databaseId')
gh run download "$run" --repo Timpan4/kubecove --name parity-coverage-map --dir e2e/artifacts
PARITY_CHANGED=origin/main bun run e2e:parity
```

`bun e2e/parity/changed-scenarios.ts <base> [<head>] [--map <path>]` prints a selection and its causes without running it.

## Equal-tests rule

A UI change in either client lands with a shared scenario that both drivers pass. `contract.test.ts` checks two invariants on every `bun test` run:

1. Every view in `visual/views.ts` has at least one scenario whose ID starts with `<view>.`. Adding a native view to the visual harness without a shared scenario fails the check.
2. Every action in `ACTIONS` (`contract.ts`) has a handler in both `web.ts` and the modules under `tests/parity/`, dispatched by `parity.rs`.

An action names user-visible behavior, not a selector. Each driver maps it to its own UI: GPUI test IDs and labels, and web roles, names and text. When an action cannot be expressed in both clients, the clients have diverged and the divergence is the bug to fix.

Native-only tests in `src-tauri/gpui/tests/native.rs` and `src-tauri/gpui/tests/native/` cover what the browser mocks cannot express: read errors, cancellation, stale asynchronous results after scope changes, sessions from other sources, dirty drafts that block closing, refused log streams and dry runs, failed guarded executions, log streams that outlive their detail, dry runs of a draft that changed before they finished, and kubeconfig settings that the native backend cannot save. Native preference tests additionally cover file-backed process restart, migration, corrupt or future documents, stale revisions and failed writes. Their paths stay in worktree-local temporary directories.

The GPUI parity driver shapes text with GPUI's `NoopTextSystem`, where every glyph is 0.6 em wide, so its text widths say nothing about the bundled fonts. Parity steps check boxes only: a value stays inside its cell, and toolbar buttons stay inside the detail panel. Checks that need real glyph widths, such as "Deployment" fitting the Kind column or the live Logs status reading in full, live in `src-tauri/gpui/tests/text_fit.rs`. It renders the exported fixture with the platform text system and the bundled fonts, on Linux only, as `tests/visual.rs` does. Run it from the worktree root with the build settings in `AGENTS.md`:

```sh
bun e2e/parity/visual/export-fixture.ts e2e/artifacts/text-fit/fixture.json
KUBECOVE_PARITY_FIXTURE="$PWD/e2e/artifacts/text-fit/fixture.json" \
  cargo test --manifest-path src-tauri/gpui/Cargo.toml --test text_fit
```

`live-data.json` replays the same scripted watch messages in both drivers. It covers resource identity, deletion, reconnect catch-up, stale read failures, permission-limited polling, scope changes, event order, and discovered custom kinds in the sidebar and picker. Native stream tests also check cancellation while opening, dropped streams, and receivers that outlive their page, detail or context. The native client reuses the typed Rust watch commands, the web's 15,000 ms recovery interval from `resource-watch.ts`, and its 250 ms refresh throttle from `live-view-refresh.ts`. Pending row patches apply at rendering without rebuilding the table's filtered rows.

The ignored `watch_burst_frame_time` native test measures a burst against the 10,000-row fixture from `visual/export-watch-burst.ts`. It reports offscreen debug CPU frame construction and executor drain time, not GPU presentation or a release frame rate. The measured frames exceed the 8.33 ms requirement. Live-data scenarios do not prove 120 fps.

The detail-tab scenarios run guarded operations only against the browser mocks. The fixture backend answers a preview or execution only when its request matches the exported one exactly, so a wrong target or a missing guard field fails the scenario instead of reaching a cluster.

The `coverage-*.json` scenarios cover workspace deletion and import collisions, palette keyboard and dismissal controls, table page and group totals, map viewport and scope controls, timeline and event searches, log layouts and stream controls, force-conflict review and diff styles, action drafts, exec and forward controls, retained sessions, Helm resource entry points, RBAC form fields and evidence, incident context and failure states, and failed kubeconfig reads and saves. Pending, partial, empty and failed reads come from `tauri-dev-mock-coverage.ts`; the native fixture exports those same responses. Log viewport scenarios request the production default tail of 200 lines, then inject a subsequent line to check Jump to latest. Clipboard checks use page-local and native in-memory substitutes.

The shared YAML editor scenario covers undo and redo, selection replacement and document Home/End keys. Both clients use the platform undo and redo shortcuts. The web editor scrolls in the detail pane; native code configures a fixed-height editor with internal scrolling. `yaml.fold-whole-block` folds blocks from the gutter, including a block at the end of the document, and checks the visible line numbers. The web reads its line-number gutter; GPUI walks the cursor with Shift+Down and copies each selection, because a folded line has no other observable state there. The GPUI YAML editor computes its fold ranges in `src-tauri/gpui/src/inspector/yaml_folds.rs` to match `@codemirror/lang-yaml`. Editing the line right after a folded block opens that fold in GPUI but not on the web, because GPUI Kit drops a fold whose last line is edited and the native fold ends on that line. Syntax and indent decoration equivalence remain unverified. In remote mode, both clients save the KUBECONFIG environment variable name, added server paths, removals, reordering and source labels through the same typed remote commands (`settings-kubeconfig.remote-env-and-server-path`, `settings-kubeconfig.remote-paths-reorder-remove-labels`). Neither client offers file picks in remote mode, because a desktop file dialog cannot choose a server path; the web hides Choose files there and GPUI does too.

## Failure modes

[Scripted backend timing](mock-timing.md) records the asynchronous failure modes,
release-gate contract, source-derived retry window and current model boundaries.

When one web scenario fails, rerun that ID alone with `PARITY_PREFIX=<id> PARITY_JOBS=1 bun run e2e:parity`, and use `PARITY_RERUN=last bun run e2e:parity` for several failures or a Vite start timeout. Do not rerun the full suite to tell a flake from a real failure. A scenario that fails in the run and passes alone is a flake; record it below with its cause. A confirmed flake is still a bug in the scenario or driver.

Confirmed flakes:

- `coverage-map.viewport` (web, full-suite load only): the zoom-in wait timed out. The failure capture showed the map at its fit zoom. The map fits itself two frames after its measured size changes, so a late fit could undo the driver's zoom click. The wait now presses zoom in again until the node grows. It never failed alone, so the fix is unproven until full runs stop showing it.

- `argo-review.retry-accepted-state` (web, under parallel load), now fixed: the app's own Argo CD state poll could succeed after the mock returned to `base` and before the driver clicked Retry state refresh. The scenario now runs `controlClock` after the review opens, and `advanceClock` runs the recovery tick only when the scenario asks for it. The web driver passed it 5 of 5 runs in a row after the change. Its pre-change flake was not reproduced here.
- `argo-connected.saved-profile-and-preference` (web): failed once in a loaded full run and passed alone.
- `mock-timing.list-watch-gap` (web): failed once with "Execution context was destroyed" on the first run after a fresh `bun install`. `vite.log` shows Vite re-optimizing dependencies and reloading the page mid-scenario. It passed alone and in the next run of the same prefixes. The same reload later failed `mock-timing.forbidden` and `mock-timing.watch-start-version` in one first run after a fresh install; both passed in the next run. It also failed `argo-workspace.watch-start-version` once when the reload, after Vite optimized `@codemirror/commands`, dropped the focused Application; it passed on `PARITY_RERUN=last`.
- `resources.table-cells` (GPUI): failed once with "resource table did not render cell:Ready:resource:ConfigMap:argocd:kube-root-ca.crt after scrolling" and passed in the next run of the same prefixes. Its cause is not yet known.

Mock parity does not prove platform clipboard integration or a live remote terminal application.

Both clients read the same `mcp-settings.json` and `mcp-token` in the desktop config directory. The MCP host stays local while a remote runtime is selected. Native tests cover occupied ports, token-file startup failure, token rotation against the read-only endpoint, enabled startup after backend recreation, corrupt or unreadable settings, failed saves and private token-file permissions. Workspace editing supports rename, primary context, group membership and namespaces while preserving the record ID, kinds, retained import fields and eligible reviews. Row details, YAML, events and guarded operations target the row's context. The ownership map shows one context at a time, chosen with a Map context select. GitOps and Helm stay on the primary context. The `resources.multi-context-*` and `map.multi-context-picker` scenarios in `e2e/parity/scenarios/resources-multi-context.json` cover this.

Native gaps remain in native update installation and platform packaging, both excluded by user decision. GPUI does not import browser preferences automatically (ADR 0030); the web has no such import either. The YAML editor marks the first serde_yaml parser error and every Kubernetes lint finding, with one lens per line. The web's `yaml` parser also reports two warnings that serde_yaml does not expose, unresolved tags and unknown directives, and every duplicate key or flow-collection error in one pass. serde_yaml returns only the first error and no warnings, so those stay native gaps until a parser with error recovery and positions is approved. The lint failure notice and the disabled Apply description match the web in the `yaml-apply.*` scenarios. The native Apply tooltip rendering is not checked visually. Preferences for unsupported native features are stored for when those features are available.

Known differences that have no shared scenario:

- GPUI does not read the platform reduce-motion setting. The web honors `prefers-reduced-motion`.
- Pins: deleting the last object of a custom kind keeps its pin in GPUI until a list of that kind completes, where the web drops it. GPUI drops a pin whose saved namespace was deleted, where the web keeps it.
- Remote error detail text differs between the clients.
- The exec terminal's right-click menu is GPUI's own. The web shows the platform webview menu, and GPUI shows Copy, Paste and Select all, which call the same paths as Ctrl+Insert, Shift+Insert and the select-all gesture. The web driver cannot open the webview menu, so `tests/native/exec_context_menu.rs` covers GPUI's menu.
- GPUI asks before closing the window with an unsaved YAML draft. The web has no close guard.
- YAML folding: editing the line after a folded block reopens the fold in GPUI. The web folds a two-line flow collection whose closing bracket has its own line, and GPUI does not. The Argo CD comparison editors keep GPUI Kit's default folds, which leave the block's last line visible.
- Remote sign-in notices update after the next failed remote call or when Settings opens. Neither desktop client receives them as pushed events.
- Resources reads (R25): GPUI stages the per-kind reads, so the first kinds show before the rest arrive. The web makes one combined `list_resource_scope` call. The staging is kept because it shows rows sooner.
- Desktop clients do not sign in to Cloudflare Access servers (ADR 0031). They say so and accept token and OIDC servers.
